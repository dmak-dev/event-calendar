# Техническое задание на календарное приложение

## 1. Общие сведения

1.1. Наименование разработки: календарное приложение с серверной и клиентской частью.

1.2. Основание для разработки: ____.

1.3. Заказчик: ____. Исполнитель: ____.

1.4. Сроки начала и окончания работ: ____.

## 2. Назначение разработки

2.1. Приложение ведёт список событий пользователя: показывает их по дням, позволяет добавлять, изменять и удалять записи.

2.2. Данные хранятся в базе SQLite, работа с ними идёт через REST API. Клиент не хранит события у себя: список загружается с сервера при открытии страницы, а каждое изменение сразу отправляется на сервер.

2.3. Приложение рассчитано на одного пользователя на настольном компьютере. Аутентификация, разграничение прав доступа и синхронизация между устройствами не предусмотрены.

## 3. Требования к серверной части

3.1. Сервер реализуется на Node.js с использованием фреймворка Express. Для связи с базой применяется драйвер sqlite3, для обмена с клиентом - JSON.

3.2. Сервер предоставляет четыре маршрута: получение списка событий, создание события, полное обновление события и удаление события по идентификатору.

3.3. Маршрут получения списка возвращает все события, упорядоченные по возрастанию даты, затем времени, затем идентификатора.

3.4. Маршрут создания события принимает название, дату, время и описание, записывает событие в базу и возвращает код 201 с созданной записью, включая присвоенный идентификатор.

3.5. Маршрут обновления заменяет все поля события по его идентификатору и возвращает обновлённую запись.

3.6. Маршрут удаления удаляет событие по идентификатору и возвращает подтверждение.

3.7. Название события обязательно и не может состоять из пробелов. Дата передаётся в формате ГГГГ-ММ-ДД, время - в формате ЧЧ:ММ.

3.8. Дата и время проверяются на существование, а не только на форму записи. Значения вида 2026-02-31, 2025-99-99, 24:00 и 99:99 отклоняются с кодом 400.

3.8.1. Дата дополнительно ограничена диапазоном от 1 января 2000 года до 31 декабря 2100 года: приложение рассчитано на планирование, а не на хранение архива.

3.9. Описание необязательно. Значение любого типа приводится к строке, отсутствующее описание сохраняется пустой строкой.

3.10. Идентификатор в адресе проверяется: принимаются только целые положительные числа. Остальные значения отклоняются с кодом 400.

3.11. Обращение к несуществующему событию при обновлении и при удалении возвращает код 404.

3.12. Схема базы создаётся при первом подключении: таблица событий с автоматически увеличивающимся первичным ключом и индекс по паре полей даты и времени. Схема создаётся одной операцией, чтобы индекс не создавался раньше таблицы.

3.13. Файл базы данных создаётся рядом с файлом сервера, если его нет. Путь может быть переопределён переменной окружения.

3.14. Сервер раздаёт статические файлы собранного клиента при наличии каталога сборки: приложение запускается одной командой на одном порту.

3.15. CORS разрешён только для клиента разработки, работающего на порту 5173. Клиент сборки обращается к API по тому же адресу, с которого открыта страница, поэтому проверка источника не участвует.

## 4. Требования к клиентской части

4.1. Клиент реализуется на Vue 3 со сборщиком Vite. Запросы к серверу выполняются библиотекой axios.

4.2. Страница содержит форму добавления события с полями названия, даты, времени и описания, а также кнопку добавления.

4.3. Поле имени обязательно, поля даты и времени заполнены по умолчанию.

4.4. Кнопка «Сейчас» подставляет текущее время в поле времени.

4.5. Предусмотрены два режима отображения: список и сетка месяца. Переключение выполняется кнопками, по умолчанию открыт список.

4.6. В режиме списка события группируются по датам: заголовок дня и события этого дня по возрастанию времени. Внутри карточки события выводятся время, название и описание, а также кнопки редактирования и удаления.

4.7. В режиме сетки выводится месяц целиком: семь столбцов по дням недели, неделя начинается с понедельника. Ячейка дня содержит число и плашки событий этого дня. Дни соседних месяцев выводятся приглушённо, текущий день выделяется рамкой.

4.8. В режиме сетки доступны переход к предыдущему и следующему месяцу и возврат к текущему месяцу.

4.9. Клик по дню в сетке подставляет эту дату в форму добавления, клик по плашке события открывает его на редактирование.

4.10. Длинное название события в ячейке сетки обрезается многоточием, полное название доступно во всплывающей подсказке.

4.11. Удаление выполняется через модальное окно подтверждения, в котором показаны дата, время и название удаляемого события.

4.12. Редактирование выполняется в модальном окне с теми же полями, что и при добавлении; после сохранения список и сетка обновляются без перезагрузки страницы.

4.13. После добавления события форма очищается, дата принимает текущее значение, время сбрасывается на 09:00.

4.14. Текущая дата для формы берётся из локального времени браузера, а не из всемирного, чтобы событие не уезжало на соседний день при смещении часового пояса.

4.15. При недоступном сервере или ошибочном ответе пользователю выводится сообщение, а не только запись в консоли браузера. Формулировка зависит от вида ошибки: для отклонённых данных предлагается проверить поля, для недоступного сервера сообщается о проблеме со связью.

4.16. Адрес API по умолчанию совпадает с адресом открытой страницы: в собранном виде клиент раздаёт сервер. Для клиента разработки запросы идут через прокси, а переменная сборки задаёт адрес вручную.

4.17. Оформление рассчитано на работу в настольном браузере и на узком экране: поля формы на ширине до 700 пикселей выстраиваются в столбик, сетка уплотняется.

## 5. Требования к структуре данных события

5.1. Событие описывается пятью полями: идентификатор, название, дата, время и описание.

5.2. Идентификатор целое число, присваивается базой автоматически.

5.3. Название и описание хранятся строками, дата в формате ГГГГ-ММ-ДД, время в формате ЧЧ:ММ. Дата и время хранятся строками, так как база SQLite не имеет отдельного типа даты, а сравнение строк в этом формате совпадает с хронологическим порядком.

## 6. Требования к обработке ошибок

6.1. Код 400 возвращается при пустом названии, несуществующей дате или времени, некорректном идентификаторе и неразобранном теле запроса.

6.2. Ошибка разбора JSON не подменяется на код 500: это ошибка клиента, тело ответа содержит признак INVALID_JSON.

6.3. Код 404 возвращается при обращении к несуществующему событию и при запросе неизвестного маршрута. Ответ на неизвестный маршрут содержит признак ROUTE_NOT_FOUND.

6.4. Код 500 возвращается при ошибке базы данных, тело ответа содержит признак DB_ERROR без подробностей.

6.5. Если база данных не открылась или схема не создалась, сервер завершает работу с сообщением в консоли, а не отдаёт ошибку на каждый запрос.

## 8. Порядок контроля и приёмки

8.1. Контракт HTTP-интерфейса проверяется набором автоматических проверок, запускаемых командой `npm test` в каталоге backend.

8.2. Проверками подтверждается пустой список на чистой базе, создание события с присвоением идентификатора, порядок сортировки, отклонение пустого названия, несуществующих дат и времени, выход даты за допустимый диапазон, приведение числового описания к строке, сохранение события без описания, ответ 400 на битый JSON, полное обновление, ответы 404 и 400 на несуществующие и некорректные идентификаторы, однократное удаление, ответ 404 на неизвестный маршрут, выдача заголовков CORS только клиенту разработки.

8.3. Проверки выполняются на отдельной базе во временном каталоге, файл backend/events.db не изменяется.

8.4. Работоспособность клиентской части подтверждается сборкой командой `npm run build` и последовательностью действий в браузере: загрузка списка, добавление события, редактирование в модальном окне, удаление с подтверждением, переключение режимов отображения, переход по месяцам, подстановка даты кликом по дню, вывод сообщения при недоступном сервере.

8.5. Вёрстка проверяется замерами в браузере на ширине 1280 и 390 пикселей: страница не имеет горизонтальной прокрутки, блоки не выходят за пределы экрана, содержимое обрезается только там, где это задано оформлением.

## 9. Требования к развёртыванию

9.1. Требуется Node.js версии 20.19 или новее.

9.2. Перед установкой зависимостей для драйвера sqlite3 должен быть разрешён запуск установочных скриптов: свежие версии менеджера пакетов блокируют их по умолчанию, и без этого нативный модуль не собирается.

9.3. Запуск приложения в режиме разработки требует двух процессов: сервер и сервер разработки клиента. Запуск собранного приложения требует одного процесса сервера.

9.4. Порядок работы приложения - локальный. Ограничение доступа к серверу не предусмотрено, секретов приложение не хранит.
